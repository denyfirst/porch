How it works

From connection
to clarity.

Here it checks our own domain. Run it yourself for the infrastructure you are responsible for.

01 / Connect

Ask what a client asks.

Handshakes at each TLS version, one request for the front page, and the DNS records a mail server reads. Nothing is sent that a browser or a mail server would not send.

02 / Examine

Grade against a named rule set.

Each check has its own rule set, and every finding cites the standard it rests on. Where no standard sets a line, the fact is reported rather than graded.

03 / Understand

Start with what matters.

Each check leads with its verdict and its findings, with the tables and limits underneath. Your own copy lets you save every report.

Get started

Your own copy,
in three steps.

Docker on the server, and nothing else: no Go, no source and no build. The compose file names the image by its digest, and the release's signature covers the compose file.

  1. Get it

    On the server: the latest release's compose file, the signed list of hashes that covers it, and the check that both are ours. The last line has to print Good "file" signature with the key SHA256:ut6bginhZ4lZINMSXNDv3vJ6fyvmDHhtnoBJH0/Nr9Y and docker-compose.yml: OK; anything else is a stop. The key comes from GitHub and its fingerprint from this page, so a key changed in one place alone prints a fingerprint that does not match. docs/verify.md says what each part proves.

    on the server 
    mkdir -p porch && cd porch
for f in docker-compose.yml SHA256SUMS SHA256SUMS.sig; do curl -fsSLO "https://github.com/denyfirst/porch/releases/latest/download/${f}"; done
curl -fsSL https://raw.githubusercontent.com/denyfirst/porch/main/.allowed_signers -o allowed_signers
ssh-keygen -Y verify -f allowed_signers -I releases@denyfirst.dev -n file -s SHA256SUMS.sig < SHA256SUMS && sha256sum --ignore-missing -c SHA256SUMS

  2. Start it

    Give the container a data directory, and start it. Docker fetches the image the compose file names by its digest and refuses any other bytes. Proof of control and a password are on from the first start, and nothing turns them off.

    on the server 
    mkdir -p porch-data && sudo chown 65534:65534 porch-data
docker compose up -d

  3. Open it

    It listens only on the server itself. Reach it through SSH, then open http://localhost:8080.

    on your computer 
    ssh -L 8080:127.0.0.1:8080 you@your-server

What you are about to run: docker-compose.yml

The file step 1 downloads and checks, shown here to be read rather than copied: the image named by its digest, so a registry cannot hand over anything else under that name; the port published on the server's own loopback; nothing in the container writable but its data directory; and every capability dropped. The comments in the file say why each line is there.

docker-compose.yml 
services:
  porch:
    image: ghcr.io/denyfirst/porch@{{.ImageDigest}}
    command:
      - "-listen"
      - "0.0.0.0:8080"
      - "-verification-secret-file"
      - "/data/secret"
      - "-access-file"
      - "/data/access"
    ports:
      - "127.0.0.1:8080:8080"
    volumes:
      - /etc/ssl/certs:/etc/ssl/certs:ro
      - ./porch-data:/data
    environment:
      SSL_CERT_DIR: /etc/ssl/certs
    read_only: true
    security_opt:
      - no-new-privileges:true
    cap_drop:
      - ALL
    restart: unless-stopped
  scan:
    image: ghcr.io/denyfirst/porch@{{.ImageDigest}}
    profiles: ["cli"]
    entrypoint: ["/porch-scan", "-verification-secret-file", "/data/secret"]
    volumes:
      - /etc/ssl/certs:/etc/ssl/certs:ro
      - ./porch-data:/data:ro
    environment:
      SSL_CERT_DIR: /etc/ssl/certs
    read_only: true
    security_opt:
      - no-new-privileges:true
    cap_drop:
      - ALL

To upgrade, run step 1 again in the same directory, then docker compose up -d: the data directory stays, and so does every record you published. The first check of a domain shows a DNS record to add. A public address, building the image yourself and everything else are in the self-hosting guide.
